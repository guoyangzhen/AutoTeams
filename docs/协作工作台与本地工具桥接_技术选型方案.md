# 协作工作台与本地工具桥接 · 技术选型方案（简化版）

> 目标：让 AutoTeams 协作工作台不仅能通过「用户配置的模型 API」工作，还能无缝调用用户本机的大量应用与工具——尤其是**能在终端里跑的 CLI 工具**（Claude Code、OpenCode、Codex CLI、Cursor CLI、Gemini CLI、Kimi Code、Pi 等，以及任意通用 shell 命令）——在本地直接执行读写修改更新删除等文件操作；同时把「上传文件 / 上传文件夹」改造为「用户提供本地路径 + 授权 + 本地守护进程校验」，实现真正的本地文件就地操作。
> 核心约束：AI 数字员工配置、Skills、项目配置仍留存后端数据库，做到**模型无关 / Agent 无关 / 本地工具无关**，最大化中立性与能力发挥。

- 文档日期：2026-08-07
- 部署形态：**云端 SaaS**（后端在云端）
- 桥接方向：**本地守护进程主动外连**（无需内网隧道）
- 本地执行方式：**CLI 工具调用为主**（通用命令 + Agentic CLI 适配器），原生文件操作兜底

***

## 1. 背景与目标

### 1.1 现状

- 后端为 FastAPI，`backend/app/api/llm_config.py` 已支持企业级「模型 API 配置」（用户可配置模型 API）。
- 协作工作台由独立 Node 服务 `collaboration-service/` 承担，基于 `@earendil-works/pi-coding-agent`（pi.dev SDK）+ AgnesAI，为每个会话创建**服务端沙箱 cwd**，工具 `read/bash/edit/write` 只在沙箱内运行，并经 WebSocket 流式回传。
- 文件 / 文件夹上传走服务端 `UPLOAD_ROOT` 暂存，`path_security.py` 负责路径安全校验。
- 企业 AI 员工配置、Skills、知识、任务等均存后端数据库。

### 1.2 期望的演进

1. **网页 ↔ 本地桥接**：云端 AutoTeams 能触发本地工具在用户机器上执行真实文件操作。
2. **本地路径授权替代上传**：用户只需提供一个精确的本地文件夹路径并开放权限，由本地守护进程校验存在性 / 合法性后就地操作。
3. **CLI 优先**：本地大量应用与工具，尤其是终端里能跑的 CLI 工具，都能被调用。
4. **配置中立**：AI 员工配置、Skills、项目配置仍留在后端 DB，不绑定任何特定模型 / Agent / 本地工具。

### 1.3 核心矛盾

Web 应用无法直接访问用户本地文件系统，存在「云端 ↔ 本地」两个信任域。破解矛盾的关键是引入一条**标准化的、带鉴权的桥接通道**，并让执行发生在本地。

***

## 2. 核心思路：本地守护进程主动外连（一条最关键的设计决策）

> **让本地守护进程"主动向外"连接云端，而不是让云端去找本地。** 这一条决策同时解决了两件事：
>
> 1. 外连**不需要 NAT 穿透/内网隧道**（cloudflared / tailscale / frp 那一整层都可以砍掉）；
> 2. 云端后端只需维护一个稳定的 WebSocket 服务端，与本地守护进程通信。

云端只负责「房间」：对话、任务、企业配置、知识、审批、审计。本地守护进程负责「干活」：在授权目录内调用用户已有的工具执行。Agent 永不掉线。

### 2.1 为什么这样最省

- 隧道层（部署、域名、证书、NAT）→ **全部取消**。
- 云端"开 MCP Server 让本地工具连进来"的反向方向 → **推迟到 P1**，P0 不做。
- 四类执行器适配 → 收敛为一个**统一的 CLI 调用抽象**，天然覆盖大部分工具。

***

## 3. 技术选型（简化后）

### 3.1 传输层：外连 WebSocket（必选，无需隧道）

- 本地守护进程作为 **WebSocket 客户端**，主动连云端 `collaboration-service` 的 `/bridge` 端点。
- 云端作为 WebSocket 服务端，鉴权后维持长连接、心跳、断线重连。
- 复用现有协作服务的 WebSocket 基础设施与事件模型（`tool_start / tool_end / artifact`）。
- **可选**：用户内网不便直连时，可用 cloudflared/tailscale/frp 兜底，但**默认不依赖**。

### 3.2 本地执行层：CLI 工具调用（核心，见 §4）

- **通用 CLI 启动器**：在授权目录内 spawn 任意命令，流式回传 stdout/stderr。
- **Agentic CLI 适配器**：封装 Claude Code / OpenCode / Codex / Pi / Cursor CLI / Gemini CLI / Kimi Code 等无头模式，统一输出回传。
- **原生文件操作**：守护进程内置 read/write/delete，仅限授权目录，作最轻量方式。

### 3.3 协议演进（可选，非 P0）

- **MCP（Model Context Protocol）** 作为远期互操作标准：若未来需要把 AutoTeams 能力暴露给任意第三方 MCP 客户端，或驱动官方 MCP Server，可叠加 `@modelcontextprotocol/sdk`。**当前阶段以 WebSocket + CLI 直调为主**，MCP 作为扩展方向。

***

## 4. 本地执行层设计（CLI 工具调用，重点）

目标是"本地的很多应用、很多工具，尤其是终端里能跑的 CLI 工具都能被调用"。设计为**统一的 CLI 调用抽象 + 可插拔适配器**。

### 4.1 统一 CLI 启动器（generic-cli）

- 在**授权工作目录**内 `spawn` 一个进程执行命令。
- 支持任意命令，但受**白名单 + 目录约束**约束（见 §9 安全）。
- **流式**回传 stdout/stderr（经现有 WebSocket 事件回传）。
- 支持长驻 / 交互式进程（可选 PTY）。
- 注入环境变量：授权 token、工作目录、会话 ID。

### 4.2 Agentic CLI 适配器（可插拔）

每个适配器负责：探测是否安装 → 拼装无头参数 → 解析结构化输出 → 映射回现有事件模型。

| 适配器                                  | 无头/自动调用方式                                 | 说明                |
| ------------------------------------ | ----------------------------------------- | ----------------- |
| `claude-code`                        | `claude -p "…" --output-format json`      | Anthropic 官方，生态成熟 |
| `opencode`                           | `opencode run "…"` / headless server      | 开源、模型无关、跨平台       |
| `codex`                              | `codex exec "…"`                          | OpenAI 官方 CLI     |
| `pi`                                 | `@earendil-works/pi-coding-agent` session | 复用现有集成            |
| `cursor-cli` / `gemini-cli` / `kimi` | 各自 CLI                                    | 按需接入              |
| `generic-cli`                        | 任意 shell 命令                               | 兜底，覆盖"其他终端工具"     |

> 统一的 `RunnerAdapter` 接口：`{ name, detect(), validateConfig(), runTask(task, ctx) }`。云端按"本地已就绪工具"动态下发任务。

### 4.3 原生文件操作（native-fs）

- 守护进程内置对授权目录的 read / write / update / delete。
- 作为最轻量执行方式：不依赖外部 CLI，适合简单文件读写与"路径校验"。

### 4.4 工具注册表

- 用户在守护进程配置中声明「可用 CLI 工具 + 允许的工作目录」。
- 守护进程上报给云端，前端展示「本地已就绪工具」卡片。

## 5. 推荐架构

```
┌────────────────────────────── 云端（AutoTeams SaaS） ──────────────────────────────┐
│                                                                                  │
│  前端 React (Vite) ──► 后端 FastAPI ──► collaboration-service (Node + pi.dev)    │
│                                        │  WebSocket 服务端 /bridge（心跳/鉴权）    │
│                                        │  会话/任务/事件 模型（复用 tool_* 事件）   │
│                                        ▲  外连（无需隧道）                         │
└────────────────────────────────────────┼──────────────────────────────────────────┘
                                         │
┌────────────────────────────────────────┴── 用户本地 ──────────────────────────────┐
│                                                                                  │
│  AutoTeams Local Runner（本地守护进程，可打包为桌面托盘 / 命令行工具）                 │
│   ├─ 外连 WebSocket 客户端（token 鉴权 + 心跳 + 断线重连）                          │
│   ├─ 本地路径授权注册（路径存在性/合法性/白名单校验 + 审计）                        │
│   ├─ RunnerAdapter 池（可插拔）：                                                  │
│   │    ├─ generic-cli（任意 shell 命令）                                           │
│   │    ├─ claude-code / opencode / codex / pi / cursor-cli ...（Agentic CLI）      │
│   │    └─ native-fs（内置 read/write/delete）                                      │
│   └─ 流式回传 tool_start/tool_end/artifact → 前端                                    │
└──────────────────────────────────────────────────────────────────────────────────────┘
```

### 5.1 数据流

```
用户输入本地路径 + 授权范围
 → 前端 POST /local-paths/register {local_path, scope}
 → 后端入库 + 审计 → 下发至 Local Runner
 → Runner 本地校验（存在性/合法性/白名单）→ 返回逻辑文件树
 → 用户给 AI 员工发任务 → 云端选择已就绪 RunnerAdapter → 下发执行请求
 → Runner 在授权目录内调用 CLI / 原生 FS 执行 → 流式回传轨迹与成果物
 → 前端实时展示（复用现有执行轨迹面板）
```

## 6. 对既有「上传文件 / 上传文件夹」的改造

### 6.1 现状链路

- 前端 `frontend/src/api/folders.ts`：`scanFolder` / `listFolderChildren` / `uploadFolder`（`webkitdirectory` 上传到服务端 `UPLOAD_ROOT`）。
- 后端 `backend/app/api/folders.py`：`/folders/upload` 暂存、`/folders/scan`、`/folders/list-children`。
- 协作服务附件：`POST /api/sessions/:id/attachments` 写入会话沙箱 `knowledge/`。

### 6.2 目标链路（本地路径授权，替代上传）

```
用户输入本地路径 + 授权范围
 → POST /local-paths/register
 → 后端入库（enterprise/user/local_path/scope/status/runner_id）+ 审计
 → 下发至 Local Runner → 本地校验（存在性/合法性/白名单）
 → 返回逻辑文件树（相对路径）
 → AI 员工通过 Runner 在本地就地 read/write/edit
 → 结果与成果物经 WebSocket 流式回传
```

### 6.3 具体改动点

- **新增本地路径授权模型**：`local_path_grant`（enterprise\_id、user\_id、label、local\_path、scope(`read`/`read_write`)、status、runner\_id、created\_at）。复用企业隔离与 RBAC。
- **新增端点**（`backend/app/api/local_paths.py`）：`POST /local-paths/register`、`GET /local-paths`、`DELETE /local-paths/{id}`、`POST /local-paths/{id}/validate`。
- **保留并弱化** `/folders/upload`：作为无本地 Runner 时的**降级通道**（云端沙箱）。`/folders/scan`、`/folders/list-children` 保留。
- **协作服务附件**：增加"从已授权本地路径直接纳入知识"通道，替代"必须先上传"。

## 10. 安全与权限设计（重点）

- **最少授权**：Runner 只操作已授权目录；`scope=read` 禁止写 / 删。
- **路径校验契约**：Runner 端复用 `path_security.py` 同等规则（拒绝符号链接、`..`、空字节、越界）。
- **CLI 白名单**：`generic-cli` 仅允许白名单命令（或仅允许在授权目录内运行），杜绝任意命令执行导致越权。
- **鉴权**：Runner 用短期 token（`RUNNER_TOKEN_TTL`）外连；每请求 / 每消息校验。
- **审计**：本地读写删除全部落审计（enterprise 隔离）。
- **会话隔离**：Runner 会话按 enterprise / user 隔离，token 绑定用户。
- **降级**：无本地 Runner 时 `/folders/upload` 仍可用（云端沙箱），不破坏既有安全边界。

## 11. 分阶段实施路线

### P0（打通最小闭环，1 个本地执行器 + 本地 FS）

- 后端 `local_paths` 模型 + 端点；`collaboration-service` 新增 `/bridge` WebSocket 服务端。
- 本地 Runner 雏形：外连 WS + 授权目录 + `native-fs`（read/write/delete）+ `generic-cli`。
- 前端：输入区本地路径选择 +「本地连接」卡片。
- 验证：用户授权本地文件夹 → AI 员工在本地读取 / 写入 → 前端实时看到轨迹与成果物。

### P1（CLI 适配器 + 执行器可插拔）

- 接入 `claude-code` / `opencode` / `codex` / `pi` 等 Agentic CLI 适配器。
- 前端：本地工具多选、权限范围、断线重连 UI 完善。
- 云端按"本地已就绪工具"动态下发任务。

### P2（生产加固）

- token 轮换、审计报表、限额（并发、路径数、操作频率）。
- 可选：MCP 扩展（把 AutoTeams 能力暴露给任意第三方 MCP 客户端）、`server-git` / `server-shell` 白名单进阶。

## 12. 风险与取舍

| 风险 / 取舍  | 说明                 | 缓解                                       |
| -------- | ------------------ | ---------------------------------------- |
| 本地执行安全   | 云端触发本地操作有越权风险      | 白名单 + 短期 token + 全量审计 + scope 分离         |
| 网络不稳定    | 外连长连接抖动打断任务        | Runner 心跳 + 断线重连 + 任务状态持久化               |
| CLI 行为差异 | 各 CLI 输出格式不同       | 统一 RunnerAdapter 接口 + 解析映射               |
| 命令注入     | generic-cli 任意命令风险 | 命令白名单 + 目录约束 + 审计                        |
| 范围蔓延     | 多 CLI 适配器改动大       | P0 先做 native-fs + generic-cli 最小闭环，再滚动扩展 |

## **四、发现的低危/设计项（非阻断，供你知悉）**

1. **Windows 下 `cli` 白名单含 Unix 命令**（`ls`/`grep`/`find` 等）在 cmd 中不可用；`echo` 等内建命令经 shell 回退可正常执行。属功能局限，非安全漏洞。

5. **开发环境需配置 `BRIDGE_INTERNAL_SECRET`** 才能用桥接功能（失败关闭副作用，`.env` 已配）。
